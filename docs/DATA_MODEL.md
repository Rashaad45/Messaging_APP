# Firestore data model

> Status: `users` and `usernames` are implemented, with rules in `firestore.rules` and tests in
> `firestore-tests/` (M2). Conversations and messages arrive in M3–M4.

```
users/{uid}                          public profile: any signed-in user can read
  username: string                   lowercase, a–z 0–9 _, 3–20 chars
  displayName: string                1–50 chars
  displayNameLower: string
  createdAt: timestamp

users/{uid}/private/devices          owner only
  tokens: map<fcmToken, timestamp>   last-seen time, used to prune stale tokens

usernames/{username}                 uniqueness lock
  uid: string                        written in the same transaction as users/{uid}

conversations/{conversationId}
  type: "direct"                     "group" later
  participants: string[]             uids; used by the array-contains list query
  participantInfo: map<uid, {displayName, username}>   denormalised for the list screen
  lastMessage: {id, text, senderId, createdAt} | null
  updatedAt: timestamp               list sort key
  unread: map<uid, number>           incremented by Cloud Function; a user may reset only their own key to 0
  readUpTo: map<uid, timestamp>      read receipts (high-water mark)
  deliveredUpTo: map<uid, timestamp> delivery receipts (high-water mark)
  typing: map<uid, timestamp>        written at most every 3 s; stale after 5 s

conversations/{conversationId}/messages/{messageId}   messageId generated by the client
  senderId: string                   must equal request.auth.uid
  type: "text"                       "image", "post_share", … later
  text: string                       1–2000 chars
  createdAt: timestamp               serverTimestamp()
```

## Key design points
- **Deterministic direct-chat ID:** `dm_{minUid}_{maxUid}`. Opening a chat with the same
  person always hits the same document, so duplicate chats can't happen and no "does a
  chat exist?" query is needed.
- **Username uniqueness:** `usernames/{name}` is the lock. The Security Rules require that
  `users/{uid}` and `usernames/{name}` be created in the same transaction (checked with
  `getAfter()`), so two users can never claim the same name.
- **Receipts:** a message shows *read* when `message.createdAt <= readUpTo[recipient]`.
  That's one write per chat opened, instead of one write per message.
- **Denormalisation:** `participantInfo` and `lastMessage` are copied into the conversation
  so the list screen needs a single query. The trade-off is that a display-name change has
  to be fanned out to every conversation (done in a Cloud Function).

## Required indexes
| Collection | Fields | Used by |
|---|---|---|
| `conversations` | `participants` (array-contains), `updatedAt` desc | Conversation list |

Single-field indexes (messages by `createdAt`, username prefix range) are automatic.

## Future extensions (no rewrite needed)
- **Groups:** `type: "group"`, random IDs, plus `name`/`photoUrl` fields. `participants` and
  the per-user maps work unchanged up to ~100 members. Larger groups would move per-user
  state into `conversations/{id}/members/{uid}` to stay under Firestore's 1 MiB doc limit
  and avoid write contention. Security rules already check membership via `participants`.
- **Media:** messages already carry `type`. An image message adds
  `media: {storagePath, width, height}`, with the files in Cloud Storage.
- **Posts / social feed:** a separate top-level `posts/{postId}` collection with
  `authorId`, plus `users/{uid}/feed/{postId}` fan-out written by a Cloud Function.
  This is independent of chat. Sharing a post into a chat would be a message with
  `type: "post_share"`.
- **E2E encryption:** `text` would become `ciphertext` plus a key-version field. The
  outbox and pending/sent flow stay the same; only the message payload changes.
